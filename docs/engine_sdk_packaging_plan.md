# Phase 5 — Engine SDK + packaging

Phases 1 to 4 of the editor-first restructure shipped; this is the only open phase. Status: **SDK spike PASSED 2026-07-31.** The gate is cleared; what remains is packaging work, not a research question.

Everything here serves *shipping to someone else*. Daily work stays on engine-source-by-default (phase 3a).

## Per-project engine workflow (2026-09-20, landed)

Decided before starting the packager, because engine fixes made from inside a project need to be trackable and pushable per project. The primitive already existed — projects name an engine checkout, engine lines are git worktrees — what was missing was a convention and editor support. Submodules and per-project engine copies were both rejected (nested checkout breaks the short-path rule; copies stop fixes propagating).

- **One engine worktree per project, on a branch named for the project.** New Project has a "Create Engine Worktree" toggle (default on). It runs `git worktree add` from the editor's own engine tree into a *sibling* folder `<EngineFolder>-<ProjectName>` on branch `project/<ProjectName>` (based on the editor's HEAD), then rebinds the project's `[engine]` section to it and registers it in `engines.ini` under the folder name. Sibling placement keeps paths short and needs no fixed folder — worktree discovery goes through git's own metadata. Failure logs and leaves the project bound to the editor's engine.
- **Engine commit pin.** `[engine] commit = <sha>` in `.gseproj`, written after every *successful game build* whose engine HEAD differs from the pin. The runtime pin lives in workspace state (seeded from the manifest at init) so the panel never reads a stale load. Verified end to end on the Throwaway project: pin equals worktree HEAD after the first build.
- **Source Control panel** (`gse.ide.source_control`, hidden by default). One section per discovered repository — project and engine worktree alike — with branch, ahead/behind, upstream state, and for the engine repo one of *unpinned / pinned / drifted from <sha7>*. Rows are the changed files with `+N -N` counts (numstat vs HEAD; untracked files count lines on disk) and a checkbox left of the name; the header checkbox selects the whole repository. Commit stages only the selected paths (batched `git add -A -- …`, message via `-F` scratch file) and Push adds an upstream to origin when the branch has none. Actions run one at a time through the git system's `task::pending` command slot; failures show at the top of the panel.
- **Git system changes that made this possible.** Status moved to porcelain v2 with branch headers (branch, upstream, ahead/behind, HEAD oid). Init/commit/push are all step lists on a root through one runner. The watcher resolves the real git dir through the `.git` *file*, so linked worktrees refresh on HEAD/index changes. Status codes and action builders are enumerator annotations, not switches.
- **Any jump-to-file reveals the Code panel.** `editor_app` also reads `jump_to_request`; it inserts the Code panel into the primary view if no window hosts it, activates its tab, and pushes `window_focus_request` so a click from a detached panel brings the code window forward.
- **Shared fix found along the way:** `layout_store::apply` accumulated one blank line per section rewrite (the separator before a removed section stayed attached to the previous one). It now trims the tail before appending, so every layout file gets exactly one separator.

The pin is also the value item 4 below should stamp; the two share a field.

## Spike result

A foreign translation unit compiled against relocated BMIs, linked against relocated libraries, and ran:

```
sdk ok: 6 m
```

Setup: the engine's 395 `.gcm` files and 5 `.a` files were copied out of `out/build/x64-mingw-gcc-RelWithDebInfo` into `%TEMP%/gse-sdk-layout` — a path with no relationship to the repo. A consumer TU in a third directory (`%TEMP%/gse-sdk-consumer`) did `import std; import gse;`, used `gse::vec3<gse::length>` and `std::println`, and produced a 197 KB object, a 589 MB executable, and correct output with the unit formatter intact.

Path A (hand-generated flags) is therefore **viable**, and needed only two direct module mappings — `gse` and `std`. Everything else resolved on its own, for the reason below.

## The finding that constrains the design

**GCC bakes each dependency BMI's path into the importing BMI, and does not re-map transitive imports through the module mapper.** Surfaced by:

```
gse.assert: error: failed to read compiled module: No such file or directory
gse.assert: note: compiled module file is 'Engine/CMakeFiles/Engine.dir/gse.assert.gcm'
```

The mapper said `gse.assert` lived at `<sdk>/Modules/gse.assert.gcm`; GCC used the path stored inside `gse.gcm` instead. A second variant confirmed it by prefixing `$root` onto that baked path rather than onto the mapped one.

The baked path is **relative**, and is resolved against the compiler's working directory:

| Image shape | Consumer cwd | Result |
|---|---|---|
| Flat `Modules/*.gcm`, every module mapped | anywhere | **fails** — transitive deps unresolvable |
| Original `Engine/CMakeFiles/Engine.dir/…` layout preserved | SDK root | **works** — all 395 BMIs load |

So the SDK image is **a relocatable copy of a build tree**, not an arbitrary directory of modules. Two consequences:

- The packager must preserve the module tree's relative layout verbatim. It cannot flatten, rename, or reorganise into a prettier `Modules/` directory.
- The consumer must compile with its root at the SDK. CMake sets the working directory to the *consumer's* build tree, so either the SDK is unpacked into that build tree at the expected relative path, or the generated project passes a root that makes the baked paths resolve. **This is the main open design question for Path B.**

## Gotchas found the hard way

- **`-fmodule-mapper=C:/…` is ambiguous with GCC's `host:port` socket syntax** and fails with no diagnostic at all. CMake always passes a *relative* mapper path; so must the packager and any generated build.
- **A mapper file with CRLF line endings maps nothing.** GCC fails every import with `unknown compiled module interface: no such module` and gives no hint the file was read at all. Python's text mode writes CRLF on Windows, which is what made the spike's relative-entry mapper look broken while an absolute one written another way worked. With LF, `$root .` plus relative entries (CMake's own modmap form) resolves from the image root. Isolated 2026-09-21; `package_engine_sdk.py` writes every text file it emits with `newline="\n"`.
- **`g++` exits non-zero with zero output** when the toolchain's own DLLs are not on `PATH`. Any packaging script that shells out to the compiler must put `<toolchain>/bin` on `PATH` first or it will look like a silent, causeless failure.
- The engine's phase-1 path resolution already behaves correctly for an install image: without `gse.manifest` the app refuses to start and says why, then works once one is supplied. The `mode = installed` hook is real, not theoretical.

## Remaining work

Ordered 2026-09-20: get one working SDK end to end on a single config before widening or polishing. Items 1–4 are the minimum viable SDK, 5–6 widen it, 7–8 are polish that depends on everything above being stable.

It reads the toolchain from the build tree's `CMakeCache.txt` rather than `~/.gcc-trunk`, always verifies, echoes each verify command into the tab, and does not zip. **Editor path verified end to end 2026-09-21** (`sdk ok: 6 m` from the button). One unexplained failure on the way: the link step reported `cannot find -ladvapi32` while the driver was spawned by its backslash path (`C:\Users\...\current\bin\g++.exe`, straight from `CMakeCache.txt` via `make_preferred`) and ld resolved itself through the junction target `gcc-trunk-v6`; the identical library list linked once the command was built from forward-slash paths. Keep spawning the driver with forward slashes until that is understood. **Agent access 2026-09-22:** `gse_package_sdk` in the MCP server drops a request into `cache/agent-build/package/`; the package system consumes it, runs the same job, and publishes the image path (or the failure) through the build inbox results, so a chat can package without a human pressing the button. The script stays as the CI form. Copy-only — it takes a build dir, the engine root and a stage dir; building stays with the build runner. Layout as built:
   | Source | Image | Rule |
   |---|---|---|
   | every BMI named in `Engine/CMakeFiles/*.dir/CXXModules.json` | same relative path | verbatim — baked relative paths (see above). Driven by the listing, not a glob: the build tree carries stale `.gcm` files from removed partitions (10 at time of writing) |
   | `Engine/lib*.a` | `Engine/` | verbatim |
   | repo `Engine/Resources` | `Engine/Resources` | read here in both modes |
   | repo `Engine/Engine` | `Engine/Source` | installed mode resolves source assets and shaders here; ship the whole folder |
   | build `Engine/Resources` | `Engine/Baked` | installed mode reads baked output here |
   | `*.dll` + `D3D12/` beside the built game exe (`<build>/<project>/`, project read from the build's `gse.manifest`) | `Bin/` | only what the build tree already produced |
   Plus `gse.manifest` (`mode = installed`, no root line) and `gse.modules`: `$root .` followed by name → relative BMI path, derived from `CXXModules.json` with the build prefix stripped. That file *is* a GCC module mapper, so `--verify` passes it straight through as `-fmodule-mapper=gse.modules` with cwd at the image root and toolchain bin first on `PATH`. The hello TU is `import std; import gse;` printing a `gse::meters` quantity; the check looks for the `sdk ok` line because the engine's log sink frames stdout with its own start/end lines. Link inputs come from the game exe's `LINK_LIBRARIES` stanza in `build.ninja`, with `Engine/` archives remapped into the image, `vcpkg_installed/` ones still taken from the build tree (item 2), and the project's own lib dropped. `--out` zips the image.
2. **Vendor the dependencies** — **DONE in the editor 2026-09-21.** Staging writes `gse.link`: the game exe's `LINK_FLAGS` plus `LINK_LIBRARIES` from `build.ninja` with the project's own archive dropped, every path left image-relative. Each `vcpkg_installed/…` archive it names is copied into the image at that same relative path, and the runtime DLLs (vcpkg's and gcc's, as `gse_copy_runtime_deps` placed them beside the game exe) already land in `Bin/`. Verify now links from `gse.link` with cwd at the image root, so it is also the consumer's link line for item 3. The Python script still links from the build tree.
3. **`[engine] version = <n>`** resolution in `project::load()`, alongside `name`, `source` and `commit`. **Spike staged 2026-09-21, hand-run pending.** Two decisions made before writing loader code:
   - *Not a junction.* Pointing `<build>/Engine` at the image looked cheap, but the build runner does `remove_all(build_dir)` when the engine dir changes, and MinGW's libstdc++ follows junctions on recursive delete — one reconfigure would wipe the shared image. The image is instead **hard-linked file by file** into the consumer's build dir (`file(CREATE_LINK … COPY_ON_ERROR)`, so a different volume degrades to a copy). Same `Engine/CMakeFiles/…` layout, so the baked relative paths resolve; no scan, no junction, nothing to delete through.
   - *CMake's own modmap wins.* CMake appends its generated `-fmodule-mapper=<obj>.modmap` after user flags, and that mapper only knows modules from targets CMake scanned, so shipped BMIs are invisible to any scanned target. Consumer targets therefore set `CXX_SCAN_FOR_MODULES OFF` and pass `-fmodules-ts -fmodule-mapper=gse.modules` themselves. Consequence: a project that adds its own `.cppm` files cannot import them through CMake's scanner while also importing the SDK; that project's own modules need a hand-maintained mapper or a Path B future. Fine for the game-code-in-`.cpp` shape the generated project template uses today.
   What was written: `Engine/cmake/GSEEngineSdk.cmake` (shipped in the image — the packager now copies `Engine/cmake` too) resolves the toolchain from the image manifest and refuses to configure if that release is not under `~/.gcc-trunk`, forces `CMAKE_CXX_COMPILER` to it, links every BMI from `gse.modules` plus the mapper into the consumer build dir, turns `gse.link` into `target_link_options`/`target_link_libraries` against the image, and writes a consumer `gse.manifest` (`mode = installed`, `root = <image>`, `project = <src>`). Engine side: installed mode now honours `root` instead of collapsing it to the build dir (`Config.cpp`), so `Engine/Source` and `Engine/Baked` resolve inside the image while the exe lives in the consumer build. The reference consumer is `Engine/cmake/SdkConsumer` (shipped in the image; a `main.cpp` printing a quantity and the resolved engine paths). **Verify now builds it 2026-09-22:** instead of hand-compiling a hello TU, the packager configures and builds the consumer under `<image>/.verify` with the cmake and ninja the build tree's cache names, runs it, and requires both the `sdk ok` line and an `engine root:` line equal to the image path — so every `gse_package_sdk` call is the item 3 test and no step is manual. **Binding landed 2026-09-22:** the image manifest carries `version = <12-hex short sha>` and the packager registers `[sdks] <version> = <image>` in the user's `engines.ini`, the same registry the `[engines]` names live in. A project's `[engine] version = <n>` resolves through that registry in `project::load()` (unregistered or missing image → `engine_problem`, same surface as a missing source tree) and wins over `name`/`source`. The worktree gains `installed`; for an installed tree `engine_root` is the image and `engine_source` is `Engine/Source`. The build runner routes installed trees to `ensure_sdk_configured`, which configures with `-DGSE_SDK_DIR` (no engine build, no vcpkg inheritance) and rebuilds the tree when the bound image changes. Generated project CMake takes both paths: `GSE_SDK_DIR` includes `GSEEngineSdk.cmake`, links modules, writes the consumer manifest, and refuses a project that declares its own `.cppm` files (scanner constraint above); otherwise it is the source-tree template as before. Existing projects keep their old CMakeLists and stay source-bound until regenerated. Not yet done: a UI to bind a project to an image (today: edit `[engine] version` in the `.gseproj` by hand), and re-testing a real project through this path — only the shipped consumer has been through it.
4. **Toolchain lockstep stamp** — **stamp written 2026-09-21, check pending on item 3.** The image manifest carries `toolchain = <release folder>` (the directory the `current` junction resolves to, e.g. `gcc-trunk-v6`, which is the install tag) and `engine = <HEAD sha>` from `git rev-parse` in the packaged engine root — the same value the `[engine] commit` pin uses, so the two share one authority. The dev manifest written by `gse_write_manifest()` stays as it was: dev mode compiles from source, so it has nothing to drift against. **Check landed 2026-09-22** in `build_runner::sdk_toolchain_bin`: before configuring an installed tree the runner compares the image's `toolchain` with the folder the editor's own compiler junction resolves to and refuses with a message naming both. The SDK CMake file refuses independently when that release is not installed. Original intent: when a project binds an image, compare the image's `toolchain` with the editor's own resolved compiler folder and fail the bind loudly on mismatch — a BMI/compiler mismatch otherwise presents as "Bad file data" on every module, and a plugin mismatch as every analyzed TU failing identically.
5. **`std.gcm` policy — DECIDED 2026-09-22: ship it.** `std` and `std.compat` are two entries in the module listing like any other and the shipped consumer imports them from the image. The exact-flags worry is gone because the SDK CMake file forces the image's compiler, build type and engine flags on every consumer target, and the toolchain stamp (item 4) refuses a different release outright. Building it consumer-side would need CMake's `import std` machinery, which depends on the scanner we turn off. Revisit only if a consumer needs different flags from the engine.
6. **Per-config trees — DONE 2026-09-22.** Not `Modules/<config>` — the baked relative paths forbid re-rooting inside an image — but one image per configuration: `dist/engine-sdk/<preset>/…`, keyed by the build tree's directory name (`x64-mingw-gcc-RelWithDebInfo`), each a complete verbatim image with its own manifest. The manifest gained `build_type = <CMAKE_BUILD_TYPE>` and the SDK CMake file forces the consumer's `CMAKE_BUILD_TYPE` from it, so neither the packager's verify nor the build runner passes one. The registry maps a version to the `dist/engine-sdk` parent, and `project::load()` picks `<parent>/<editor's own preset>`; a version packaged only for another preset reports that as the engine problem. Packaging from a Debug build tree therefore produces a sibling Debug image under the same version.
7. **`install()` / `export()` rules.** Moved down from first: the spike showed the image must be a verbatim copy of the build tree layout, which is what a copy script does naturally and what install rules tend to fight. The benefit is a CMake-native `find_package` consumer, which is really Path B — do it after Path A works, if at all.
8. **Homegrown installer — LANDED 2026-09-22; stage one and the gui boot verified 2026-09-23, the Install button not yet exercised.** Inno Setup was dropped in favour of a self-extracting setup built from the engine itself. The packager's last step builds two targets, `Installer` (the gui) and `Setup` (the stub), copies `Installer.exe` into the image's `Bin/`, copies the stub to `dist/engine-sdk/GSEngine-<version>-<preset>-setup.exe` and appends the staged image as a pack: one LZMS blob per file (Windows Compression API via `libcabinet`), a reflection-serialised table (`gse::binary_writer`) and a fixed trailer at the very end, so the stub reads its own payload by seeking back from EOF (`gse.sdk:pack`). The stub (`Installer/Setup/Main.cpp`) links `-static` and imports only `gse.sdk` and the win32 wrappers, so it runs on a machine with none of the image's DLLs; `ldd` shows system DLLs only. It extracts `Bin/`, `Engine/Resources` and `Engine/Baked` into `%LOCALAPPDATA%\GSE\cache\installer\<version>\<preset>\`, writes an installed-mode manifest there and starts `Bin/Installer.exe --payload <setup exe>`. The gui (`installer:screen`) has a destination field defaulting to `%LOCALAPPDATA%\GSE\sdk\<version>`; the image lands at `<destination>/<preset>` so the editor's `<parent>/<preset>` lookup holds, with a progress bar drawn from the background `task::pending`. It then registers `[sdks]` (now `gse.sdk:registry`, which the editor delegates to), writes `gse.install` (file list) and adds an HKCU `Uninstall\GSEngineSDK-<version>-<preset>` entry pointing at `Bin/Installer.exe --uninstall`, so it shows in Windows Apps. Uninstall is headless: deletes the recorded files, unregisters, removes the key and hands the folder to a temp `.cmd` that retries `rmdir` after exit (the running `Installer.exe` is removed there). Toolchain bundling and updates remain open.
   Two engine changes were needed to get here. **The logger is now constructed on first use** (`log::instance()`, a function-local static in `Log.cpp`), not at static init: its constructor resolves `config::logs_dir()`, and anything linking the binary archive reaches it through `assert_fail`, so the manifest-less stub aborted before `main`. `logger_retired` distinguishes "destroyed" (fall back to stderr) from "not built yet" (build it). **Render boots bake missing built-ins** (`bake_missing_built_ins` ahead of `verify_built_ins`): dev mode only baked an asset when something loaded it, so a built-in nothing had loaded yet (the Geist italics) was absent from the build tree, got packaged absent, and the installed gui asserted. The packager also drops `*_atlas_debug.png` from `Engine/Baked` (~100 MB off the setup exe).

## Path B

`install(TARGETS … FILE_SET CXX_MODULES)` + `find_package` remains untried. It is the newest corner of CMake's module support and GCC is the least-exercised compiler in it, so it should be attempted *after* the packager works via Path A rather than bet on. The baked-path constraint above applies to it identically — whatever CMake generates still has to make those relative paths resolve.
