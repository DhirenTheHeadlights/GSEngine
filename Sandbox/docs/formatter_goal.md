# Goal: Canonical formatting, one construct at a time

## Aim
Make the code panel's Format and format-on-save produce the owner's chosen layout for most or all syntactic block kinds in the codebase. The work goes one construct at a time, the same way annotation blocks were done: agree on a canonical shape for a construct, teach `Engine/Code/Source/Format/Formatter.cppm` to emit it, then confirm the result on real files. Literal text and identifiers are never changed. Only whitespace, line breaks and ordering move, and ordering only where the owner has approved a rule for it, as with the import sort.

## Pass criteria
1. **Catalogue.** This record keeps a list of construct kinds. Each entry is marked `agreed-format`, `implemented`, `verified` or `out-of-scope (owner)`. The starting list is: annotation blocks (already implemented, real-file check pending), import blocks, brace/indent of namespaces/structs/functions, enum bodies, aggregate/designated initializer lists, function signatures and long parameter lists, long call-argument wrapping, lambdas (captures, bodies passed as arguments), `requires`/template headers, `switch`/`case`, blank-line policy between members/functions, and `if constexpr`/`else` chains. Steering may add kinds it finds in the tree.
2. **Each construct is verified on real files.** For each `implemented` kind, a steering run formats at least 3 real files that contain it, chosen from different modules. It must confirm three things. (a) The output matches the agreed shape, shown as a before/after excerpt in the ledger. (b) A second format produces zero edits. (c) An Editor and Sandbox `gse_build` succeeds with the formatted files. Only then does the kind move to `verified`.
3. **No regression.** Every previously `verified` kind still gives zero edits on its sample files after each later construct lands.
4. **Done.** The goal is met when every catalogue entry is `verified` or `out-of-scope (owner)`, and the owner confirms the overall result. That confirmation is the `owner` criterion.

## Charter
- **No asking needed:** editing `Engine/Code/Source/Format/Formatter.cppm` and the format plumbing in `Editor/Editor/Source/App/CodePanel.cppm`, plus any new formatter-only helper files under `Engine/Code/Source/Format/`. The `gse_format` agent tool and its plumbing (owner-approved 2026-11-14): `Tools/gse-mcp/server.mjs`, the `formats` queue in `Editor/Editor/Source/BuildRunner/Inbox.*`, `Editor/Editor/Source/FormatQuery/`, and its phase/flavor entries in `Editor/Editor/Source/Agent/Session.cppm` and `Model.cppm`. Queuing builds through `gse_build`. Running format on sample files to verify, then **reverting those sample files** unless the owner has asked to keep the reformat. Updating this record's ledger and catalogue states.
- **Must ask the owner (`gse_ask`) every time:** the canonical shape of each new construct. A format is never chosen unilaterally. Offer 2+ concrete layouts drawn from what the codebase already does most, with a recommendation. Also ask before any rule that reorders tokens or touches non-whitespace, and before any mass reformat that commits formatting changes across the tree.
- **Off limits:** `settings.ini`, other chats' files, any formatting of files outside the formatter's verification samples beyond what the owner approved, comments in code (none, per CLAUDE.md), and any change to `docs/STYLEGUIDE.md` without approval. The style guide should be updated to describe each agreed format, but only with the owner's approval of the wording.
- **Process for each construct:** survey real occurrences, ask for a format, implement the smallest pass that composes with the existing pipeline (import sort, then annotations, then indentation; new passes take the format options so tabs/spaces follow the setting), verify per criterion 2, record the result in the ledger.
